unconfirmed value MUST be rendered from a placeholder constant so it
can be edited in one place later (see /data files below). Never hardcode
a fake clinic address, fake years of experience, fake reviews, or fake
statistics anywhere in code, metadata, or structured data.

3. TECH STACK
--------------------------------------------------------------------
- Framework: Next.js 14+ (App Router), TypeScript
- Styling: Tailwind CSS (utility-first, no heavy CSS framework)
- Fonts: next/font with a variable sans-serif (e.g. Inter or Plus
  Jakarta Sans) — self-hosted via next/font, no external font CDN
  requests, no render-blocking font loads
- Icons: lucide-react (lightweight, tree-shakeable)
- Forms: native React state + server action (or simple API route),
  NO third-party form SaaS embedded as an iframe (keeps page light and
  avoids third-party tracking scripts by default). Provide the form
  handler with a clearly marked TODO for the real submission target
  (email service / serverless function) since no backend is being
  built in v1 — see Section 8.
- No database. No authentication. No admin dashboard. No CMS.
- Deployment target: Vercel (or any static/Node hosting) — must build
  cleanly with `next build` and produce zero console errors/warnings.
- Package manager: npm. Keep dependencies minimal — do not add UI
  kits, animation libraries, or analytics SDKs by default.

4. DESIGN SYSTEM (theme reference: client-supplied mobile UI moodboard —
   deep forest green + warm cream, rounded cards, circular icon
   buttons, bold stat callouts — a "TOTUM"-style premium services app
   aesthetic, adapted for healthcare)
--------------------------------------------------------------------
Palette:

  --color-forest-900: #16241F   (deep dark green — dark card panels,
                                  header/footer bg, primary buttons)
  --color-forest-800: #1E332C   (secondary dark surface, hover states)
  --color-forest-600: #2F5245   (mid-tone green, used sparingly for
                                  borders/dividers on dark panels)
  --color-cream-50:   #F6F2E9   (primary page background — warm,
                                  not pure white)
  --color-cream-100:  #EFE9DA   (alternating section background)
  --color-ink-900:    #12140F   (near-black, high-contrast headings
                                  on cream/white surfaces)
  --color-slate-600:  #4A5049   (body text on light backgrounds)
  --color-white:      #FFFFFF   (card surfaces on dark panels, header
                                  bar on light sections)
  --color-border:     #E3DCC9   (hairline borders on cream surfaces)
  --color-gold-accent:#C9A227   (rare accent — a small badge/icon
                                  highlight only, e.g. an award or
                                  "trusted" icon; never a background
                                  or large fill)
  --color-success:    #2E9E6B   (form success state)
  --color-error:      #B3412E   (form error state — warm red-brown,
                                  not a jarring pure red, to match tone)
  --color-whatsapp:   #25D366   (WhatsApp CTA only — the one brand
                                  color allowed outside this palette)

Rules:
- Two-surface system, matching the reference: DARK PANELS (forest-900
  background, white/cream text, white circular icon buttons) alternate
  with LIGHT PANELS (cream-50 background, ink-900 text, forest-900
  buttons). Do not mix — each section/card is clearly one or the other.
- Cards are prominently rounded: 24–28px radius on large panel cards
  (hero card, trust card, stat cards), 12–16px on smaller components
  (form fields, service cards). This is a defining trait of the
  reference — do not flatten it to sharp corners.
- Circular icon buttons (44–56px) are a signature element: white
  circle + forest-900 icon on dark panels, forest-900 circle + white
  icon on light panels. Use these for the call icon, menu icon, and
  small feature-badge icons — not generic square icon buttons.
- Bold stat-style callouts: large (36–48px) bold numerals paired with
  a small label underneath, exactly like the reference's "108 / Team
  members" pattern. IMPORTANT: only use this pattern for numbers we
  can actually confirm — currently that's just the 5 km service
  radius ("5 / km service radius"). Do NOT invent "years of practice,"
  "successful cases," or "patients treated" numbers to fill this
  pattern. Where the reference uses a second/third stat, substitute a
  non-numeric feature badge instead (e.g. an icon + "Home Visits" or
  icon + "BPT Qualified") rather than fabricate a statistic.
- Typography: bold, tight-tracking sans-serif headlines (600–700
  weight, large scale — 32–44px on mobile hero text), calm regular-
  weight body copy (1.6+ line-height, minimum 16px).
- A short pull-quote/intro-line component (like the reference's "We
  understand the business..." card) may be reused for a brief,
  factual professional-introduction line from Chinmay — never a
  fabricated patient testimonial.
- Subtle thin-line geometric background accents (as in the reference)
  are allowed behind hero/dark sections at very low opacity — never
  busy, never competing with text contrast.
- Shadows: soft, warm-toned, used only under cards sitting on cream
  backgrounds; dark panels rely on the color block itself, not shadow.
- Iconography: simple line icons (lucide-react) inside the circular
  buttons/badges described above — not filled medical clip-art, not
  photographic icons.
- Imagery: real photography only when supplied by Chinmay, treated
  the way the reference treats its portrait (clean cutout/crop against
  a plain card background, not a busy stock scene). Until real photos
  exist, use clean placeholder blocks (cream-100 or forest-800
  background + a lucide icon + label like "Portrait photo — to be
  added"), never stock photos of unrelated people presented as
  Chinmay or as real patients.

8. CTA / CONTACT BEHAVIOR
--------------------------------------------------------------------
Call button: <a href="tel:+919113285572">
WhatsApp button: <a href="https://wa.me/919113285572" target="_blank"
  rel="noopener noreferrer">. Do not prefill a message unless the
  client later approves specific wording — if a prefilled message is
  wanted now, use a neutral line only:
  https://wa.me/919113285572?text=Hi%20Chinmay%2C%20I%27d%20like%20to%20enquire%20about%20home%20physiotherapy
  (URL-encoded, editable in one constant).

Enquiry form (route: /contact, section id="enquiry-form"):
Fields: Name (required), Phone number (required, basic pattern
validation for Indian numbers), Preferred contact method (Call /
WhatsApp — radio), Message / general enquiry (required, textarea),
Preferred date/time (optional, plain text or simple date input — not
a full booking calendar). NO medical history, medication, or diagnosis
fields.

Client-side validation: required fields, phone pattern, max length
guards, disable submit while pending, show inline error text (not
just color) for accessibility.

Submission target: since there is no backend/database in v1, wire the
form to one of these (pick ONE, document the choice in a code comment
at the top of the form component, and leave the endpoint as an env
var so it's swappable):
  a) A serverless API route (/app/api/enquiry/route.ts) that emails
     the enquiry using a transactional email provider (e.g. Resend)
     via an API key read from process.env — NEVER hardcode the key in
     client code, only use it server-side.
  b) A privacy-respecting form backend (e.g. Formspree/Web3Forms) via
     its documented POST endpoint.
Either way: do not store submissions in a database, do not log full
form contents to third-party analytics, and rate-limit/basic
honeypot-field spam protection (a hidden field bots fill in but humans
don't) must be included since there's no CAPTCHA dependency.

On success: show an inline confirmation message ("Thanks — Chinmay
will get back to you shortly") plus repeat the Call/WhatsApp buttons
as a fallback. On failure: show a clear error and the phone number as
a fallback contact method — never let a form failure be a dead end.

11. ACCESSIBILITY REQUIREMENTS
--------------------------------------------------------------------
- Color contrast: all text meets WCAG AA against its background using
  the palette in Section 4 (verify navy-700 on white, white on
  navy-900/teal-600, etc. — do not use teal-100 text on white).
- Visible focus states on every interactive element (custom focus
  ring using teal-600, not just browser default suppressed).
- All buttons/links have accessible names (no icon-only buttons
  without aria-label, e.g. WhatsApp icon button needs
  aria-label="Message Chinmay on WhatsApp").
- Form inputs have associated <label> elements (not placeholder-only
  labeling), and errors are announced via aria-live or aria-describedby.
- Mobile bottom action bar must not overlap or trap focus; verify tab
  order remains logical with it present.
- Minimum tap target 44x44px on mobile.
- No content conveyed by color alone (e.g. required-field asterisk +
  text, not just red color).

--------------------------------------------------------------------
